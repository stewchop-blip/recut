# ReCut — Agent Instructions

## 1. Что это за проект

ReCut — Telegram-бот для работы с короткими видео.

Основной сценарий пользователя:

1. Пользователь отправляет ссылку на видео из поддерживаемой платформы.
2. Бот скачивает видео.
3. Пользователь получает исходное видео или запускает его обработку.
4. ReCut создаёт изменённую версию видео.
5. Пользователь получает готовый файл обратно в Telegram.

Поддерживаемые или планируемые источники:

- TikTok
- Instagram Reels
- YouTube Shorts
- другие источники, если их добавление не ломает текущую архитектуру

Проект уже существует.

НЕ создавай новый проект, нового Telegram-бота, новый GitHub-репозиторий или новую инфраструктуру без явной необходимости.

## 2. Главный принцип работы

Сначала изучай существующий проект.

Перед серьёзными изменениями:

- прочитай этот `AGENTS.md`;
- изучи структуру репозитория;
- посмотри существующие зависимости;
- изучи конфигурационные файлы;
- посмотри текущую реализацию нужной функции;
- при необходимости посмотри git history;
- найди уже существующие вспомогательные функции и сервисы.

Не переписывай рабочие части проекта только потому, что можешь сделать их иначе.

Предпочтительный подход:

**минимальное изменение → проверка → исправление ошибок → commit → push**

## 3. GitHub и деплой

GitHub является основным репозиторием проекта.

Railway уже связан с GitHub.

Стандартный процесс деплоя:

`изменение кода → тестирование → git commit → git push → Railway auto-deploy`

Для обычного деплоя:

- НЕ используй `railway up`;
- НЕ требуй авторизацию пользователя в Railway;
- НЕ проси Railway Token;
- НЕ создавай новый Railway project;
- НЕ создавай новый Railway service.

Если push успешно отправлен в ветку, используемую Railway, Railway должен самостоятельно запустить deployment.

Если после push deployment не начинается, сначала проверить:

1. В какую Git-ветку отправлены изменения.
2. Успешен ли `git push`.
3. Есть ли изменения в GitHub.
4. Какая ветка подключена к Railway.
5. Не изменились ли конфигурационные файлы проекта.
6. Нет ли очевидных ошибок сборки.
7. Есть ли доступные deployment/build logs.

Только если проблема действительно требует прямого управления Railway, объясни пользователю:

- зачем нужен прямой Railway-доступ;
- какую конкретно операцию невозможно выполнить через существующую GitHub-интеграцию.

Не менять существующую инфраструктуру без причины.

## 4. Разрешения агента

В рамках существующего проекта агент может самостоятельно:

- читать файлы проекта;
- анализировать код;
- редактировать код;
- создавать необходимые файлы;
- удалять явно устаревший код, если это безопасно;
- устанавливать необходимые зависимости;
- выполнять команды терминала;
- запускать локальные проверки;
- запускать тесты;
- исправлять обнаруженные ошибки;
- работать с Git;
- делать commits;
- делать push в существующий GitHub-репозиторий.

Не нужно спрашивать пользователя после каждого небольшого изменения.

Если задача понятна, доводи её до максимально законченного состояния самостоятельно.

## 5. Перед внесением изменений

Перед реализацией новой функции сначала определить:

- есть ли уже похожая реализация;
- есть ли нужная библиотека в dependencies;
- можно ли использовать существующий модуль;
- не нарушит ли изменение другие функции;
- нет ли похожего решения в уже подключённом коде.

Не дублировать код без необходимости.

## 6. Использование готового open-source кода

Если функция сложная, разрешается искать существующие open-source решения и библиотеки вместо написания всего с нуля.

Особенно это относится к:

- скачиванию видео;
- обработке видео;
- FFmpeg;
- определению формата видео;
- работе с metadata;
- масштабированию;
- crop;
- padding;
- overlays;
- субтитрам;
- обработке аудио;
- работе с Telegram media;
- очередям обработки;
- временным файлам.

При использовании стороннего репозитория:

1. Не копировать проект целиком без необходимости.
2. Найти конкретную рабочую реализацию нужной функции.
3. Проверить лицензию.
4. Изучить зависимости.
5. Взять только необходимые идеи или компоненты.
6. Адаптировать их под архитектуру ReCut.
7. Не тащить лишние зависимости.

Предпочтение отдаётся:

- популярным;
- активно поддерживаемым;
- понятным;
- относительно компактным решениям.

## 7. Скачивание видео

Один из основных сценариев ReCut:

`ссылка → скачивание → Telegram`

Система должна стремиться поддерживать:

- TikTok;
- Instagram Reels;
- YouTube Shorts.

При реализации скачивания:

- использовать наиболее устойчивый существующий подход;
- предусматривать ошибки источника;
- предусматривать недоступное или удалённое видео;
- предусматривать private content;
- предусматривать ограничения платформ;
- предусматривать изменение структуры URL;
- не падать всем ботом при ошибке одного скачивания.

Если одна библиотека перестала работать, сначала исследовать альтернативы, а не переписывать весь pipeline.

## 8. Видеообработка

ReCut должен уметь создавать обработанную версию видео.

Основной инструмент для обработки видео предпочтительно:

`FFmpeg`

или существующая библиотека поверх FFmpeg, если она уже используется в проекте.

Pipeline должен быть модульным.

Например:

`input → download → probe → transforms → overlay → encode → output`

Каждый этап по возможности должен быть отдельной функцией или модулем.

## 9. Возможные изменения видео

Архитектура должна позволять применять комбинацию изменений.

Примеры:

- resize;
- crop;
- небольшое масштабирование;
- padding;
- изменение canvas;
- изменение aspect ratio;
- небольшая коррекция изображения;
- overlay;
- баннер;
- текст;
- логотип;
- background;
- изменение расположения кадра;
- обработка аудио;
- изменение metadata;
- перекодирование.

Не применять случайные агрессивные эффекты, которые ухудшают качество видео.

Качество результата важнее количества трансформаций.

## 10. Баннеры и overlays

ReCut должен поддерживать добавление рекламной или информационной плашки к видео.

Плашка может находиться:

- снизу видео;
- в свободном поле;
- внутри canvas;
- поверх изображения, если это предусмотрено конкретным шаблоном.

Система overlays должна быть отделена от основного downloader.

Желательно иметь возможность в будущем добавлять:

- PNG overlays;
- прозрачные PNG;
- текстовые overlays;
- анимированные overlays;
- несколько шаблонов;
- разные позиции.

Если overlay уже реализован, исправлять существующую реализацию, а не создавать параллельную вторую систему.

## 11. Форматы видео

Нужно учитывать разные соотношения сторон:

- 9:16
- 4:5
- 1:1
- другие вертикальные форматы

Не обрезать важный контент без необходимости.

При преобразовании формата предпочтительно использовать:

- scale;
- crop;
- padding;
- background;

в зависимости от задачи.

## 12. Качество

Итоговое видео не должно заметно ухудшаться после обработки.

Следить за:

- resolution;
- bitrate;
- FPS;
- audio quality;
- aspect ratio;
- codec compatibility.

Предпочтительный формат выдачи:

- MP4
- H.264
- AAC

если текущая архитектура проекта не требует другого формата.

Видео должно нормально воспроизводиться в Telegram и на распространённых мобильных устройствах.

## 13. Telegram

Telegram-бот является пользовательским интерфейсом проекта.

При изменениях:

- не ломать существующие handlers;
- не менять команды без необходимости;
- сохранять понятный UX;
- давать пользователю понятное сообщение при ошибке.

Не показывать пользователю:

- traceback;
- технические exception;
- внутренние пути;
- API keys;
- tokens;
- server details.

Технические ошибки должны уходить в logs.

## 14. Временные файлы

Видео может занимать много места.

После завершения обработки временные файлы необходимо удалять.

Это относится к:

- исходным загрузкам;
- intermediate video;
- extracted audio;
- thumbnails;
- temporary overlays;
- output files после успешной отправки.

Очистка должна происходить также при большинстве ошибок.

Предпочтительно использовать `try/finally` или эквивалентный безопасный механизм.

## 15. Параллельные задачи

Не предполагать, что бот всегда обрабатывает только одного пользователя.

Избегать общих временных имён вроде:

`video.mp4`

Использовать:

- unique IDs;
- request IDs;
- user/job scoped folders.

Два пользователя не должны перезаписывать файлы друг друга.

## 16. Безопасность

Никогда не:

- публиковать API tokens;
- коммитить secrets;
- выводить secrets в logs;
- хранить credentials в исходниках.

Secrets должны находиться в environment variables.

Перед commit проверять, что случайно не добавлены:

- `.env`;
- tokens;
- API keys;
- cookies;
- session files;
- credentials.

## 17. Ошибки

Каждая внешняя операция может завершиться ошибкой.

Особенно:

- загрузка видео;
- сеть;
- Telegram API;
- FFmpeg;
- сторонние API;
- файловая система.

Ошибки должны обрабатываться локально.

Одна неудачная обработка не должна приводить к остановке всего бота.

## 18. Logging

Logging должен помогать понять этап, на котором произошла проблема.

Полезные события:

- request received;
- URL detected;
- download started;
- download completed;
- processing started;
- FFmpeg started;
- processing completed;
- Telegram upload started;
- Telegram upload completed;
- cleanup completed.

При ошибке логировать:

- этап;
- тип ошибки;
- request/job id.

Не логировать чувствительные данные.

## 19. Проверка после изменений

После каждой существенной задачи:

1. Проверить изменённый код.
2. Проверить imports.
3. Проверить syntax.
4. Запустить существующие tests.
5. Если тестов нет, сделать хотя бы минимальную локальную проверку.
6. Проверить основные пользовательские сценарии.
7. Исправить обнаруженные ошибки.

Не делать commit заведомо неработающего состояния.

## 20. Git

Перед началом работы:

`git status`

Перед commit:

- посмотреть diff;
- убедиться, что не добавлены лишние файлы;
- убедиться, что нет secrets;
- проверить изменённый код.

После этого:

`git add`
`git commit`
`git push`

Commit message должен кратко описывать реальное изменение.

Примеры:

`fix video download pipeline`

`add overlay processing`

`fix temporary file cleanup`

`improve ffmpeg error handling`

## 21. Не делать без необходимости

Не нужно:

- переписывать проект с нуля;
- менять язык программирования;
- менять framework;
- создавать новый Telegram bot;
- создавать новый GitHub repository;
- создавать новый Railway project;
- менять deployment architecture;
- менять database;
- менять работающие API;
- проводить большой refactoring ради красоты.

Если текущая архитектура работает, улучшай её постепенно.

## 22. Если задача кажется сложной

Не останавливаться сразу с вопросом пользователю.

Сначала:

1. Исследовать существующий код.
2. Найти причину проблемы.
3. Проверить документацию библиотек.
4. Найти существующие open-source реализации.
5. Попробовать разумное решение.
6. Проверить результат.

Обращаться к пользователю только если действительно требуется решение, которое невозможно безопасно принять самостоятельно.

## 23. Если задача уже частично реализована

Если функция существует, но работает неправильно:

НЕ создавай рядом новую функцию с нуля.

Сначала найди:

- существующий handler;
- service;
- helper;
- FFmpeg pipeline;
- downloader;
- config.

Затем исправь текущую реализацию.

Приоритеты проекта:

1. Надёжность.
2. Рабочее скачивание видео.
3. Стабильная обработка.
4. Хорошее качество итогового файла.
5. Быстрая обработка.
6. Понятный Telegram UX.
7. Простота дальнейшего добавления функций.

## 25. Основной пользовательский flow

Целевой сценарий:

`Пользователь отправляет ссылку`

↓

`ReCut определяет источник`

↓

`ReCut скачивает видео`

↓

`Пользователь получает действия`

↓

`Скачать оригинал / обработать`

↓

`ReCut запускает video pipeline`

↓

`ReCut создаёт готовое видео`

↓

`ReCut отправляет его пользователю`

↓

`Временные файлы удаляются`

Этот flow нельзя ломать при добавлении новых функций.

## 26. Правило завершения задачи

Не считать задачу законченной сразу после изменения исходного кода.

Задача считается законченной после:

`реализация → проверка → исправление ошибок → commit → push`

Если deployment происходит автоматически через GitHub, отдельно вручную деплоить приложение не нужно.
